# Status Cutover Runtime Firebase ke Supabase

**Checkpoint:** 22 Oktober 2026
**Source branch:** `codex/supabase-runtime-cutover-20261022`; kode runtime yang diuji pada commit `21140c3`
**Supabase target:** project `ptsasgdvgrbdtgyqieie`
**Tujuan:** mencatat batas cutover, migrasi database yang sudah diterapkan, dan syarat aman untuk melanjutkan PR #11.

## Bukti CI terbaru — 22 Oktober 2026

Commit `21140c3` lulus pada [GitHub Actions run #39778292353](https://github.com/hamdanfaiz/ERP4-Pesantren/actions/runs/39778292353). Kedua job selesai dengan sukses:

- Typecheck, build client/server, pemeriksaan bahwa Firebase bukan dependensi produksi, gate Firebase Admin di luar development, serta smoke test production tanpa paket Firebase.
- Build dan startup image Docker, validasi konfigurasi Compose, dan smoke test container.
- Supabase lokal terisolasi: database tests/pgTAP, reservasi NIS serentak, API auth dan isolasi tenant, alur HTTP unggah bukti Finance ke Storage, serta backup/restore database lokal.

**Batas bukti:** CI memakai Supabase lokal dan data sintetis. Run tersebut sendiri tidak menerapkan migrasi ke project pelanggan, tidak menguji kredensial pelanggan, dan tidak membuktikan end-to-end semua modul/role pada environment non-produksi. Migrasi ke project target dilakukan terpisah setelah run CI, dengan hasil dicatat di bagian “Migrasi Supabase yang sudah diterapkan” di bawah. Tidak ada feature flag runtime yang diaktifkan atau record operasional pelanggan yang diubah. Catatan modul di bawah yang menyebut migrasi “belum diuji” berarti alur modul belum teruji penuh pada environment pelanggan, kecuali bukti di bawah menyatakan lain.


## Keputusan arsitektur

Supabase menjadi tujuan autentikasi, database operasional, dan penyimpanan berkas. Setiap instalasi pelanggan menggunakan proyek Supabase yang dikelola pelanggan atau stack Supabase mandiri. Runtime frontend kini Supabase-only; Firebase masih diperlukan oleh endpoint impor/rekonsiliasi legacy di backend sampai migrasi selesai dan dependensinya dapat dihapus.

## Master Data dan asrama

Working tree lokal kini menambahkan API Supabase untuk membaca/menyimpan/mengarsip Santri serta membaca/menyimpan/menghapus Gedung, Kamar, dan Kelas. Server mewajibkan token Supabase, profil aktif, tenant pada profil, permission modul, dan Admin/SuperAdmin untuk perubahan; semua query dijalankan dengan `tenant_id` dari profil tepercaya. NIK/NISN diproses server-side dengan `PII_ENCRYPTION_KEY` dan `PII_FINGERPRINT_KEY`, tidak disimpan di browser storage. Onboarding kandidat diterima memakai kontrak yang sama melalui RPC dan menghubungkan PPDB dengan Master Data/asrama tanpa melewati reservasi NIS. Frontend dapat membaca dan menulis melalui jalur ini saat `VITE_SUPABASE_MASTER_DATA_RUNTIME_ENABLED` dan `SUPABASE_MASTER_DATA_RUNTIME_ENABLED` sama-sama aktif. Pada mode tersebut UI hanya menampilkan kategori yang sudah memiliki kontrak API, tidak menampilkan data contoh untuk kategori tersebut, dan tidak menggunakan draft formulir PII dari `localStorage`. Jalur legacy kini mengikat draft autosave ke tenant dan user, menolak pemulihan jika salah satu identitas berbeda, menghapus format draft lama yang tidak memiliki user, serta membersihkan semua draft Master Data saat runtime Supabase aktif.

Kategori selain Santri, Gedung, Kamar, dan Kelas disembunyikan dari runtime sampai API Supabase tersedia. Impor CSV lokal dan aksi massal di browser telah dilepas agar perubahan tidak tampak berhasil tanpa persistensi. Jalur lama yang tersisa tidak dirutekan oleh aplikasi. Draft autosave Master Data dibersihkan saat runtime Supabase aktif. Form Gedung/Kamar/Kelas mengirim callback sukses setelah penyimpanan Supabase, sehingga daftar induk ikut diperbarui dan modal tertutup.

Peta struktur `StructureHierarchyD3` hanya membaca endpoint Supabase tenant untuk Gedung/Kamar/Kelas; fallback Firestore telah dihapus.

Snapshot asrama dan alokasi/penghapusan alokasi kamar memakai API serta RPC tenant-scoped melalui feature flag Supabase. Izin asrama memiliki skema tenant-scoped, event audit, RPC idempoten, layar khusus, dan impor legacy preview/apply Admin dengan fingerprint. Daftar izin Ustadz hanya mencakup santri di lokasi aktif yang ditugaskan; pengajuan serta perubahan status diperiksa ulang oleh RPC. Kedisiplinan memakai RPC idempoten untuk pencatatan/resolusi/impor dan menolak identitas ambigu, bukti non-HTTPS, serta konflik. Kehadiran malam memakai sesi tanggal; Admin harus memilih tanggal snapshot karena koleksi Firestore lama tidak menyimpan tanggal sesi, dan konflik identitas/kamar menghentikan apply. Penugasan gedung/kamar Ustadz dikelola Admin dan akses lokasi diperiksa server serta RPC. Working tree kini juga memiliki migrasi tabel, event audit, API, UI, dan RPC untuk audit kebersihan serta tiket fasilitas. Impor Admin membaca maksimal 1.000 record per jenis langsung dari Firestore server-side, menyelesaikan nama kamar hanya jika cocok unik dengan Master Data Supabase, mengikat apply ke fingerprint preview, serta menolak konflik secara atomik; snapshot pelapor/pemeriksa historis dipertahankan tanpa mengarang identitas akun. Flag runtime dan import `SUPABASE_BOARDING_FACILITY_OPS_*` dan `VITE_SUPABASE_BOARDING_FACILITY_OPS_*` tetap `false`. Migrasi belum diterapkan atau diuji. Data lokal yang belum tersinkron ke Firestore masih perlu jalur terpisah. Musyrif lama masih perlu port UI/read path, dan fungsi asrama lain belum seluruhnya pindah. Jangan aktifkan runtime asrama penuh sebelum musyrif dan sisanya dipindahkan atau dipagari.
